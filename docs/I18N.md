# Claus Internationalization

This document describes the planned frontend internationalization (i18n) direction for Claus: `next-intl` without locale-prefixed routing, English as the source locale, Korean as the first translation, and a locale resolution policy that respects account settings, cookies, and the environment. It is a design contract for the Next.js frontend (the user UI at `/` and the Console at `/console`). It is not a translation style guide, not a Django translation guide, and not a description of current behavior.

## Status

Planned. Nothing in this document is implemented beyond the literal `<html lang="en">` noted under "`<html lang>` and accessibility". Verified against the repository and the library documentation on 2026-10-08:

- `frontend/package.json` lists no i18n library. `next-intl` is not installed and `package-lock.json` does not resolve it.
- No `i18n/` folder, no `messages/` folder, no `middleware.ts` or `proxy.ts`, no `cookies()` or `headers()` usage, no Server Actions, and no route handlers exist under `frontend/src`.
- `frontend/src/app/layout.tsx` hard-codes `<html lang="en">`.
- The backend keeps the `startproject` settings: `LANGUAGE_CODE = "en-us"`, `TIME_ZONE = "UTC"`, `USE_I18N = True`, `USE_TZ = True` (`backend/config/settings.py`). No translation catalogs exist, and the only API payloads are the static health responses.
- `next-intl@4.14.9` is the latest release on the npm registry. Its peer dependency ranges (`next`: `^12.0.0 || ^13.0.0 || ^14.0.0 || ^15.0.0 || ^16.0.0`; `react`: a range that includes `^19.0.0`) accept the repository's resolved `next 15.5.19` and `react 19.2.7`.

Installing `next-intl` changes `package.json` and `package-lock.json`. That needs explicit approval under the guardrails in [CONTEXT.md](CONTEXT.md). Its dependency tree includes native packages (`@swc/core`, `@parcel/watcher`), so the install must be verified in every environment that runs `npm run build` or `npm run test:visual`.

This document covers the product UI. The language policy for repository documents (Korean and English versions of human-facing documents) is set in [CONTEXT.md](CONTEXT.md) and is unrelated to runtime i18n.

## Library and app responsibilities

`next-intl` provides message hooks, ICU message formatting, date, number, and list formatting, a request-scoped configuration function, and a client provider. It does not decide which locale a request gets, where preferences are stored, how missing translations fall back, or whether translation files agree with each other. Those are Claus responsibilities.

| Concern | Library (`next-intl`) | Claus (app code, Planned) |
|---|---|---|
| Message rendering | `useTranslations`, `getTranslations`, ICU syntax | Message catalogs, key conventions, review |
| Request configuration | `getRequestConfig` in `i18n/request.ts`, executed once per request | Locale resolution order, validation, time zone choice |
| Client Components | `NextIntlClientProvider` inherits `locale`, `messages`, `now`, `timeZone`, `formats` from a Server Component parent | Deciding which messages reach the client |
| Locale from headers | Automatic locale negotiation exists only in the routing middleware (`createMiddleware`), which Claus does not use | Parsing `Accept-Language` in app code |
| Missing translations | Reports `MISSING_MESSAGE` through `onError`, renders `getMessageFallback` (default `namespace.key`) | English fallback by merging catalogs |
| Type safety | `AppConfig` augmentation checks keys against the source-locale messages at compile time | Cross-locale parity check script |
| Preference storage | None | Cookie written by a Server Action, account preference API |

## Locales and preference values (Planned)

- Canonical and fallback locale: `en`. English messages are the source of truth.
- Supported locales: `en`, `ko`. Locale identifiers are BCP 47 language tags; Claus uses the bare language subtags; the `Accept-Language` rule maps regional variants (`ko-KR`, `en-US`) to them by primary subtag, while the account setting and the cookie must hold the bare tag.
- User preference values: `system`, `en`, `ko`. `system` means "follow the environment language".
- Adding a locale means adding a message catalog, extending the supported list, extending the parity check, and running the verification in [TESTING.md](TESTING.md). It is not a configuration flag.

The conceptual shape that carries these values is `PresentationPreferences` in [STATE-SCHEMA.md](STATE-SCHEMA.md): `subject_ref`, `ui_locale_preference`, `resolved_ui_locale`, `resolution_source`, `time_zone`, `ai_output_language_preference`; STATE-SCHEMA.md is authoritative for its field names and enumerations. Nothing persists it today.

## Locale resolution order (Planned)

The locale for a request is resolved on the server, once per request, inside `getRequestConfig`. The first source that yields a supported locale wins:

1. Signed-in account setting, when it is `en` or `ko`. A setting of `system` means "follow the environment language", so resolution skips the cookie and goes to step 3; a stale cookie from an earlier manual choice never overrides it. No account setting (signed out) falls through to step 2.
2. Explicit locale cookie, when its value is `en` or `ko`. Not consulted when the account setting is `system`.
3. Environment language: the `Accept-Language` request header, read on the server.
4. English (`en`).

The winning source is recorded as `resolution_source` (`account`, `cookie`, `environment`, `default`) for diagnostics.

Rules:

- Every candidate value is untrusted input. It is checked against the supported list before use and otherwise ignored; an unsupported or malformed value never produces an error page and never reaches a dynamic `import()` path. This is the validation discipline of `SEC-INJ-001` in [SECURITY-ARCHITECTURE.md](SECURITY-ARCHITECTURE.md) applied to locale input. The `next-intl` documentation example `store.get('locale')?.value || 'en'` performs no validation and must not be copied as-is.
- `Accept-Language` parsing is app code. Per RFC 9110, the header is a comma-separated list of language ranges with optional `q` weights (default `1`); `q=0` marks a range as not acceptable. Claus picks the highest-weighted acceptable range whose primary language subtag is a supported locale (`ko-KR;q=0.9` matches `ko`), ignores malformed ranges, and falls through when nothing matches. `next-intl` lists `negotiator` and `@formatjs/intl-localematcher` among its dependencies, but its own negotiation is part of the routing middleware; Claus does not treat transitive dependencies as public API.
- `navigator.language` in the browser is not a resolution source. The server has already rendered by the time client code runs; using it would change the locale after hydration. It may pre-select an option in a future preference UI, nothing more.
- Reading `cookies()` or `headers()` in the root layout opts every route into dynamic rendering (both are Next.js 16 request-time async APIs). Claus accepts this for the authenticated app shell; it is a known cost, not a surprise.
- The signed-in account setting requires an account model and a preference API. Neither exists. Saving a preference is a state-changing operation and is authorized on the server (`SEC-AUTH-001`).
- The cookie is written only from a Server Function (a Server Action is one) or a Route Handler, because Next.js cannot set cookies during Server Component rendering and HTTP does not allow setting cookies after streaming starts. The cookie name, lifetime, `SameSite`, and `Secure` attributes are decided with the implementation.

Illustrative example, not implemented:

```ts
// frontend/src/i18n/request.ts (shape only)
import {cookies, headers} from 'next/headers';
import {getRequestConfig} from 'next-intl/server';

const SUPPORTED = ['en', 'ko'] as const;
type Supported = (typeof SUPPORTED)[number];

function asSupported(value: string | null | undefined): Supported | null {
  return SUPPORTED.includes(value as Supported) ? (value as Supported) : null;
}

export default getRequestConfig(async () => {
  const account = await accountLocale(); // 'system', 'en', 'ko', or null when signed out
  const cookie = account === 'system' ? null : (await cookies()).get('locale')?.value;
  const locale =
    asSupported(account) ??                                          // 1. account setting
    asSupported(cookie) ??                                           // 2. explicit cookie, skipped for `system`
    fromAcceptLanguage((await headers()).get('accept-language')) ??  // 3. app-side parsing
    'en';                                                            // 4. fallback

  const en = (await import('../../messages/en.json')).default;
  const messages =
    locale === 'en' ? en : deepMerge(en, (await import(`../../messages/${locale}.json`)).default);

  return {locale, messages, timeZone: 'UTC'};
});
```

`accountLocale`, `fromAcceptLanguage`, and `deepMerge` stand for app code that does not exist. The dynamic import is safe only because `locale` has already been narrowed to the supported list.

## URLs without a locale prefix (Planned)

Claus uses the `next-intl` setup without locale-based routing (the library's documentation names the two setups "with" and "without locale-based routing"). The locale comes from app logic, not from the URL:

- `/` and `/console` keep their paths. No `[locale]` segment is added, and the rewrites in `frontend/next.config.ts` for `/core/*` and `/agent/*` are unaffected.
- Links use `next/link` and `next/navigation` directly.
- Changing the locale means changing its source (the cookie through a Server Action, or the account setting through the preference API) and re-rendering. It is a server round trip, not client-only state.
- A shared URL shows each viewer their own locale. Per-locale static generation and locale-specific SEO are not goals for an authenticated collaboration surface.

The following belong to the routing setup and are not part of the Claus design: the `next-intl` APIs `defineRouting`, `createMiddleware` (in `proxy.ts` or `middleware.ts`), `createNavigation`, `hasLocale` against `routing.locales`, and `setRequestLocale`, together with the Next.js `next/root-params` and `generateStaticParams` usage that setup requires. Introducing any of them changes this contract and needs a documented decision first.

## Server and client rendering consistency (Planned)

- `getRequestConfig` runs during the Server Components render and is cached per request with React `cache`, so every Server Component in a request sees the same locale, messages, time zone, and `now`.
- `NextIntlClientProvider` is rendered from the root layout (a Server Component) and inherits `locale`, `messages`, `now`, `timeZone`, and `formats`. Client Components therefore render with the values the server used. Passing a different `locale` on the client, or reading one from browser state, produces hydration mismatches and is not allowed.
- `onError` and `getMessageFallback` are functions and are not inherited by Client Components. If client-side reporting of missing messages is wanted, it needs a small `'use client'` wrapper provider, as the library documents; the server-side handlers live in `getRequestConfig`.
- By default `NextIntlClientProvider` sends all messages to the client. Claus prefers translating in Server Components and passing rendered strings down, and uses `messages={null}` or a picked subset where client bundles must stay small. The exact split is decided per feature, not globally in advance.
- `<html lang>` and the provider locale come from the same resolved value (`getLocale()` in the root layout).
- `useNow` or `getNow` plus an explicit `timeZone` keep relative times and formatted dates identical on both sides; see the dates section below.

## `<html lang>` and accessibility

- Fact today, with no test asserting it: `frontend/src/app/layout.tsx` renders `<html lang="en">` as a literal. This is correct while English is the only language.
- Planned: `lang` is set from the resolved locale in the root layout and always equals the locale given to `NextIntlClientProvider`. Assistive technology, hyphenation, spell checking, and CJK font selection depend on it.
- Both supported locales are left-to-right; `dir` stays `ltr`, and right-to-left layout is out of scope.
- Korean text needs its own visual pass: font stack, line breaking, and the width of translated labels in the responsive layouts and in both color schemes. These are Playwright visual checks under [TESTING.md](TESTING.md), not assumptions.

## Messages and the Korean translation (Planned)

- `messages/en.json` is the source catalog. `messages/ko.json` is a translation of it, key for key. New strings are written in English first; a Korean entry without an English source is a defect.
- Keys are stable identifiers grouped by namespace (feature or component), not English sentences. Namespace keys cannot contain `.` because `next-intl` uses it for nesting.
- Messages use ICU syntax: `{name}` arguments (alphanumeric and underscore only), `plural`, `selectordinal`, `select` (values alphanumeric and underscore; map `-` to `_` before passing a locale-like value), and rich-text tags rendered with `t.rich`. ICU MessageFormat requires the `other` branch in `plural` and `select` (the `next-intl` documentation states it for `select`).
- `t.raw` with `dangerouslySetInnerHTML` is not used for translated UI copy. Translations are reviewed like code because tags in them become React elements.
- Missing-translation policy: the library default reports `MISSING_MESSAGE` through `onError` and renders `namespace.key`. There is no built-in cross-locale fallback. Claus merges the English catalog under the Korean one when providing messages in `getRequestConfig`, so a missing Korean string renders English, and treats `MISSING_MESSAGE` as an error in development and in automated checks (no CI pipeline exists in the repository today) rather than silently shipping fallbacks. Both halves are app code.
- `t.has(key)` is for strings that intentionally exist only in some locales; it is not a substitute for the merge policy.
- Translation management tooling (editors, hosted services, AI-assisted translation) is not chosen. Catalogs stay in the repository next to the code until a workflow is needed.

## Parity validation between locales (Planned, nothing exists)

`next-intl` TypeScript augmentation (`declare module 'next-intl' { interface AppConfig { Locale; Messages; Formats } }`, with `Messages: typeof en`) makes `t('...')` calls fail compilation for keys missing from the English source and, with the experimental `createMessagesDeclaration` plugin option, for missing arguments. It validates code against `en.json` only. It does not check that `ko.json`:

- has the same key set (no missing or orphan keys),
- uses the same argument names in each message,
- uses plural and select branches that are valid for the locale,
- keeps rich-text tag names identical,
- parses as ICU at all.

A separate parity check is required before Korean ships. It compares every non-English catalog against `en.json`, allows locale-specific plural branch sets (see below), and fails `npm run lint` (and any CI pipeline; none exists in the repository today) on differences. No such script, npm script, or test exists in the repository; adding one is a frontend tooling change that follows the approval rules in [CONTEXT.md](CONTEXT.md). The verification cases are listed under internationalization testing in [TESTING.md](TESTING.md).

## Dates, times, and numbers (Planned)

- Timestamps cross the API as ISO 8601 strings in UTC. The backend already runs with `USE_TZ = True` and `TIME_ZONE = "UTC"`. The frontend parses with `Date` and formats for display; it never builds date strings by concatenation.
- `timeZone` is set explicitly in `getRequestConfig`, from the user's `time_zone` preference when one exists and otherwise from an application default. The library default is the server runtime's time zone, which makes rendered dates depend on where the server runs and lets them differ from the browser.
- Relative times ("2 hours ago") use `useFormatter().relativeTime` with `useNow` (optionally `updateInterval`). A global `now` is provided in tests so output is deterministic; in production `useNow` defaults to the current time.
- Global `formats` (`dateTime`, `number`, `list`, `displayName`) are defined once, referenced by name in code and in messages (`{orderDate, date, short}`), and typed through `AppConfig.Formats`.
- Numbers go through `format.number` or `{value, number}` in messages, never through `toString()` or manual grouping.
- Plural categories come from CLDR through `Intl.PluralRules`. For cardinal plurals English has `one` and `other` (its ordinal categories, used by `selectordinal`, are `one`, `two`, `few`, `other`); Korean has only `other` in both. A Korean message therefore has fewer branches than its English source, and `=0`-style exact matches remain available in both. The parity check compares the required branches per locale rather than demanding identical branch lists.

## Machine values are never translated (Planned)

Translation changes labels, never meaning. These stay locale-independent everywhere (storage, APIs, logs, URLs, tool schemas):

- Identifiers and references (`task_id`, `context_id`, and the like).
- Enum values such as Task status (`queued`, `running`, `waiting_for_approval`), context types, Artifact types, and the five scope names: personal, topic, team/project, organization, external.
- Permission names, role names, and scope checks.
- Error codes returned by `/core/*` or `/agent/*`. An error response carries a stable machine code; the frontend maps the code to a localized label at the rendering edge and shows the raw code when no label exists. Developer messages in responses are not user-facing copy.
- WebMCP tool `name`, input schema property names, enum values in schemas, and machine-readable results. The spec recommends localizing `title` and says nothing about localizing the other fields; Claus follows that through the UI locale and never changes `name` for a locale. See [WEBMCP.md](WEBMCP.md) and `SEC-AGENT-002`.
- Log lines, audit records, and Task error summaries.

Mapping is done with a `select` message or one key per value, always with an `other` branch that falls back to the code. A translation string carries no identifier, permission, or instruction, so a wrong or malicious translation can change what a person reads but not what the system does.

## UI locale and AI output language are separate (Planned)

- `ui_locale_preference` decides the language of the product chrome: navigation, buttons, status labels, dialogs, dates.
- `ai_output_language_preference` decides the language a user wants AI conversation replies and generated results in. It is passed to the orchestration layer as part of the request context; the frontend locale is not used to infer it.
- The two may differ: a user with a Korean UI may want English artifacts for an English-speaking team, and a team Topic may have a working language that differs from each member's UI locale. When a Topic-level working language is designed, it belongs to the collaboration context, not to `PresentationPreferences`.
- Messages written by people and AI in a Thread are stored and shown as written. The UI locale does not translate conversation content, Files, or Artifacts.
- No LLM provider or orchestration exists, so this is a contract only. Where the preference lives at runtime is decided together with the orchestration design in [ARCHITECTURE.md](ARCHITECTURE.md).

## Presentation preference policy (Planned)

`PresentationPreferences` in [STATE-SCHEMA.md](STATE-SCHEMA.md) is the conceptual shape for these preferences; its fields are listed under "Locales and preference values" above, and STATE-SCHEMA.md is authoritative for the field names and enumerations. It is not persisted, exposed, or edited anywhere today.

- Users: choose `ui_locale_preference`, `time_zone`, and `ai_output_language_preference` in account settings once a preference API exists. `system` keeps the environment language and is the default for new accounts.
- Signed-out visitors: cookie, then environment, then English. No preference is stored server-side.
- Administrators: organization- or team-level defaults, when designed, are a separate policy object, as [STATE-SCHEMA.md](STATE-SCHEMA.md) states. They apply where a user has made no explicit choice; an explicit user choice is not overridden by an administrator default. The precedence between an administrator default and a cookie is an open decision.
- Preference reads and writes go through the Django control plane like any other product operation, with server-side authorization (`SEC-AUTH-001`).

## Not implemented

None of the following exists in the repository:

- `next-intl` in `frontend/package.json` or `package-lock.json`, and the `createNextIntlPlugin` wrapper in `frontend/next.config.ts`.
- `frontend/src/i18n/request.ts` or any `getRequestConfig`.
- A `messages/` folder, `en.json`, or `ko.json`; any Korean translation.
- `NextIntlClientProvider` in the root layout; `<html lang>` derived from a locale.
- A locale cookie, the Server Function or Route Handler that writes it, or any `cookies()` or `headers()` usage.
- An account model, a preference API, or a settings UI for `PresentationPreferences`.
- An `Accept-Language` parser.
- A locale switcher component.
- A message parity validation script or lint rule.
- Explicit `timeZone`, `now`, or global `formats` configuration.
- i18n tests: the single English-language scenario (`frontend/tests/visual/home.spec.ts`) runs in four desktop/mobile × light/dark Chromium projects, without testing locale switching; the backend tests cover health, ASGI routing, database configuration, and storage only.

## Adoption checklist (Planned)

Before any i18n code is merged:

1. Approval for the dependency change (`next-intl` and its lockfile delta), per [CONTEXT.md](CONTEXT.md).
2. The resolution order, cookie attributes, and default time zone written down in this document as decided. "Planned" becomes "Implemented" only for the parts that have code and tests.
3. English catalog, Korean catalog, and the parity check landing together.
4. Playwright coverage for both locales: `/` and `/console` render, `<html lang>` matches, no console errors, no overflow from longer or shorter labels, in light and dark color schemes. The existing `home.spec.ts` assertions on English text must pin the locale (cookie or `Accept-Language` in the browser context) so they stay deterministic.
5. Backend untouched: no Django translation catalogs, no `LANGUAGE_CODE` change, and no model or migration work are part of frontend i18n adoption.

The verification cases themselves are in [TESTING.md](TESTING.md). Changes to locale input handling are a security review trigger in [CODE-REVIEW.md](CODE-REVIEW.md).
